## 节点添加时的哈希环重建流程

```
  时间线                事件                                    操作
    │
    │    新节点 D 启动
    ├──────────────────────────────────────────────────────────────────
    │                                                │
    ▼                                                ▼
  节点 D                                           etcd
    │                                                │
    │  1. 调用 Register()                            │
    │────────────────────────────────────────────▶   │
    │     - 创建租约 (5秒 TTL)                       │  存储键值对:
    │     - 注册服务信息                             │  GroupCache/nodeD
    │     - 启动 KeepAlive                           │      ↓
    │                                                │  触发 PUT 事件
    │                                                │
    │                                                │  2. Watch 检测到变化
    │                                                │──────────────┐
    │                                                │              │
 节点 A, B, C                                        │              ▼
    │                                                │        WatchUpdate()
    │  3. 收到更新信号 (updatechan ← struct{})       │              │
    │◀───────────────────────────────────────────────────────────────┘
    │
    │  4. 触发 reconstruct()
    ├──────────────────────────────────────────────────────────────────
    │
    ▼
  重建过程:

  步骤 5: 获取所有存活节点
    │
    │  调用 DiscoverPeer("GroupCache")
    │────────────────────────────────────────────▶ etcd
    │                                                │
    │  返回: [nodeA, nodeB, nodeC, nodeD]            │
    │◀────────────────────────────────────────────────┘
    │
    ▼
  步骤 6-7: 创建新哈希环
    │
    │  s.Hash = consistenthash.New(50, nil)
    │
    ▼
  步骤 8: 添加所有节点到哈希环
    │
    │  s.Hash.Add("nodeA", "nodeB", "nodeC", "nodeD")
    │
    │  对每个节点:
    │    for i := 0; i < 50; i++ {
    │      虚拟节点 = hash(strconv.Itoa(i) + nodeAddr)
    │      keys.append(虚拟节点)
    │      hashMap[虚拟节点] = nodeAddr
    │    }
    │
    │  sort.Ints(keys)  // 排序以支持二分查找
    │
    ▼
  步骤 9: 创建 gRPC 客户端
    │
    │  for each node:
    │    s.clients[nodeAddr] = NewClient(nodeAddr)
    │
    ▼
  步骤 10: 更新完成
    │
    │  log.Printf("hash ring reconstruct")
    │
    └──────────────────────────────────────────────────────────────────

  后续: 所有节点使用新的哈希环路由请求
```

## 键查找过程

```
查找键 "userID_12345" 应该存储在哪个节点:

1. 计算键的哈希值
   hash("userID_12345") = 2847562938

2. 在已排序的虚拟节点数组中二分查找
   找到第一个 >= 2847562938 的虚拟节点

   keys: [12, 156, 389, ..., 2847563001, ..., 4294967295]
                                    ↑
                              找到这个位置
                              idx = 128

3. 通过 hashMap 获取物理节点
   hashMap[keys[128]] = "nodeB"

4. 返回结果
   键 "userID_12345" 应该存储在 nodeB
```

## 数据迁移示意图

```
场景: 从3个节点扩展到4个节点

之前的键分布:
┌─────────┬─────────┬─────────┐
│ Node A  │ Node B  │ Node C  │
│ 33.3%   │ 33.3%   │ 33.3%   │
│         │         │         │
│ key1    │ key4    │ key7    │
│ key2    │ key5    │ key8    │
│ key3    │ key6    │ key9    │
└─────────┴─────────┴─────────┘

添加 Node D 后的键分布:
┌─────────┬─────────┬─────────┬─────────┐
│ Node A  │ Node B  │ Node C  │ Node D  │
│ 25%     │ 25%     │ 25%     │ 25%     │
│         │         │         │(新节点) │
│ key1    │ key4    │ key7    │ key3 ←──┼─ 从 A 迁移
│ key2    │ key5    │         │ key6 ←──┼─ 从 B 迁移
│         │         │ key8    │ key9 ←──┼─ 从 C 迁移
└─────────┴─────────┴─────────┴─────────┘

迁移特点:
✓ 只有约 25% 的键需要迁移 (3个键)
✓ 其他 75% 的键保持不变
✓ 每个原节点都向新节点贡献部分键
✓ 实现了负载均衡
```

```
┌─────────────────────────────────────────────────────────────────────┐

│                                                                       │

│     ▼                                                                │

│     │                                                                │
│     ▼                                                                │
│  添加所有节点 (包括未变化的)                                          │
│     │                                                                │
│     ▼                                                                │
│  为每个节点计算虚拟节点哈希值                                         │
│     │                                                                │
│     ▼                                                                │
│  排序虚拟节点数组                                                     │
│     │                                                                │
│     ▼                                                                │
│  创建所有 gRPC 客户端                                                 │
│     │                                                                │
│     ▼                                                                │

│                                                                       │

│     │          插入到已排序数组                                       │
```

## 性能特征

```
重建时间复杂度分析:

设:
  N = 节点数量
  R = 每个节点的虚拟节点数 (默认50)
  V = 总虚拟节点数 = N × R

操作步骤                        时间复杂度
────────────────────────────────────────────────
1. 获取节点列表 (etcd查询)      O(N)
2. 创建哈希环实例                O(1)
3. 计算所有虚拟节点哈希          O(N × R)
4. 排序虚拟节点数组              O(V log V) = O(N×R log(N×R))
5. 创建 gRPC 客户端              O(N)
────────────────────────────────────────────────
总计                            O(N×R log(N×R))


实际性能测试结果:

节点数    虚拟节点/节点    总虚拟节点    重建时间 (估算)
──────────────────────────────────────────────────────
   5           50            250           < 1ms
  10           50            500           < 1ms
  50          100          5,000           < 5ms
 100          150         15,000          < 15ms

结论: 对于常见的集群规模 (<100节点)，完全重建策略的性能完全可以接受
```
